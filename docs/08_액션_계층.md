# Action 계층 (Kinetic Layer)

## 왜 필요한가

팔란티어 Foundry 온톨로지는 세 계층으로 구성된다.

| 계층 | 구성 | 이 프로젝트 |
|---|---|---|
| **Semantic** (의미) | Object Type, Property, Link Type | 구현됨 (`ontology/schemas/objects`, `links`) |
| **Kinetic** (운동) | **Action Type**, Function, 동적 보안 | **이 문서** |
| **Dynamic** (동적) | 시계열·실시간 상태 | 부분 (TimescaleDB) |

Foundry에서 가장 차별적인 부분은 Kinetic Layer다. 사용자는 데이터베이스에
직접 UPDATE 쿼리를 던질 수 없고, **정의된 Action Type을 통해서만 상태를
바꿀 수 있다.** Action이 데이터 수정 권한을 캡슐화하기 때문에 권한·감사·
시뮬레이션이 자동으로 따라온다.

의미 계층만 있으면 "그래프 DB가 붙은 분석 시스템"이고,
운동 계층이 있어야 "온톨로지 기반 운영 시스템"이 된다.

## 핵심 원칙

> **상태 변경은 오직 Action을 통해서만 일어난다.**

서비스가 그래프/DB에 직접 쓰면:
- 누가 무엇을 왜 바꿨는지 알 수 없다
- 권한을 걸 지점이 없다
- 변경 전에 결과를 미리 볼 수 없다
- 되돌릴 근거가 없다

## 구성

```
ontology/schemas/actions/*.yaml     액션 타입 정의 (계약)
        │
        ▼
common/actions/
  types.py      ActionTypeDef / Principal / ActionRequest / ActionResult
  registry.py   YAML 로드 + 핸들러 등록
  executor.py   권한 -> 검증 -> 수행 -> 감사
  audit.py      감사 기록 (InMemory / Postgres)
        │
        ▼
api/src/services/action_handlers.py  실제 수행 로직
api/src/routers/actions.py           HTTP 진입점
        │
        ▼
action_audit 테이블 (infra/postgres/init.sql)
```

정의(YAML)와 구현(핸들러)을 분리한 이유는 온톨로지 스키마가 도메인
담당자가 읽고 고칠 수 있는 형태로 남아야 하기 때문이다.
핸들러가 없는 액션 타입은 "선언됐지만 미구현"으로 목록에는 보이되
수행은 거부된다.

## 수행 순서

순서는 고정이다. 바꾸면 통제가 새는 곳이 생긴다.

```
1. 액션 타입 조회      없으면 404
2. 권한 확인           없으면 403  (감사 기록 남김)
3. 파라미터 검증        실패 시 422 (감사 기록 남김)
4. 사유(reason) 확인   reasonRequired 인 경우
5. 핸들러 수행         dry_run 이면 쓰기 없이 예상 변경만
6. 감사 기록           성공/실패 무관하게 항상
```

**거부된 시도도 감사에 남긴다.** "누가 무엇을 하려다 막혔는가"가
"누가 무엇을 했는가"만큼 중요하다.

## 정의된 액션 타입

| 액션 | 대상 | 사유 필수 | 권한 |
|---|---|---|---|
| `VerifyRelationship` | Relationship | O | process_engineer, equipment_engineer, ontology_admin |
| `RecordExpertRelationship` | Relationship | O | process_engineer, equipment_engineer, ontology_admin |
| `AcknowledgeAlarm` | Alarm | X | operator, process_engineer, equipment_engineer, shift_supervisor |
| `UpdateEquipmentState` | Equipment, Chamber | O | equipment_engineer, shift_supervisor, ontology_admin |
| `HoldLot` | Lot | O | process_engineer, shift_supervisor, quality_engineer |
| `RequestInspection` | Equipment, Chamber | O | process_engineer, equipment_engineer, shift_supervisor |

### VerifyRelationship — 가장 전형적인 액션

통계로 발견된 관계를 `pending`에서 `verified`/`rejected`로 옮긴다.
"누가, 언제, 무엇을, 어떤 근거로 검증했는가"가 반드시 남아야 하는
통제된 상태 변경이다. 이것이 남지 않으면 그래프의 관계를 신뢰할 근거가 없다.

### UpdateEquipmentState — 전이 규칙이 스키마에 있다

SEMI E10 상태를 자유롭게 바꾸면 가동률 집계가 무너진다.
`update_equipment_state.yaml`의 `transitions`가 허용 전이를 고정한다.

특히 **정비·고장 종료 후 곧바로 `PRODUCTIVE`로 갈 수 없다.**
`STANDBY` 또는 `ENGINEERING`을 거쳐 검증한 뒤 생산에 투입한다.

### HoldLot / RequestInspection — 사람 확인 필요

`requiresHumanConfirmation: true`. 에이전트가 자동 실행할 수 없다.
생산에 직접 영향을 주기 때문이다.

## API

```
GET  /api/actions                        액션 타입 목록 (수행 가능 여부 포함)
GET  /api/actions/{action_type}          상세 (에이전트 도구 정의로도 사용)
POST /api/actions/{action_type}/simulate 쓰기 없이 예상 결과만
POST /api/actions/{action_type}          수행
GET  /api/actions/audit/recent           최근 감사 기록 (거부된 시도 포함)
```

### 예시

```bash
# 시뮬레이션 — 아무것도 쓰지 않는다
curl -X POST localhost:8000/api/actions/HoldLot/simulate \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
        "parameters": {"lot_id": "LOT-A1234", "hold": true, "hold_code": "Q-07"},
        "reason": "챔버2 유량 이상 구간 통과"
      }'

# 응답
{
  "action_type": "HoldLot",
  "succeeded": true,
  "dry_run": true,
  "changes": [
    {"object_type": "Lot", "object_id": "LOT-A1234",
     "field": "status", "before": null, "after": "ON_HOLD"},
    {"object_type": "Lot", "object_id": "LOT-A1234",
     "field": "hold_code", "before": null, "after": "Q-07"}
  ],
  "message": "[시뮬레이션] Lot LOT-A1234 를 홀드 합니다",
  "audit_id": "..."
}
```

`changes`는 `before`/`after`를 함께 담는다. 감사 기록만 보고도
무엇이 어떻게 바뀌었는지 알 수 있고, 되돌릴 근거가 된다.

## 인증 — Action은 "누가"를 요구한다

`api/src/auth.py`. JWT(HS256) 클레임:

```json
{
  "sub": "hong.gildong",
  "roles": ["process_engineer"],
  "name": "홍길동",
  "exp": 1790000000
}
```

인증이 없으면 `Principal`을 만들 수 없고, 따라서 액션도 수행할 수 없다.
**그것이 의도된 동작이다.**

### 개발 모드

`AUTH_DEV_MODE=true`이면 토큰 없이 고정 주체(`dev.user`)로 동작한다.
기동 시 경고가 남는다. **운영에서는 반드시 꺼야 한다.**
켜져 있으면 감사 기록의 "누가"가 무의미해진다.

### 에이전트가 수행하는 경우

토큰에 `is_agent`, `on_behalf_of`를 실으면 감사 기록에 그대로 남는다.
"에이전트가 홍길동을 대신해 수행했다"가 기록된다.

## 감사 기록

`action_audit` 테이블 (DDL: `infra/postgres/init.sql`).

| 컬럼 | 내용 |
|---|---|
| `audit_id` | 기록 ID |
| `action_type` | 액션 타입 |
| `principal_id`, `principal_roles` | 누가 |
| `parameters` | 무엇을 (JSONB) |
| `reason` | 왜 |
| `changes` | 무엇이 바뀌었나 (before/after, JSONB) |
| `dry_run` | 시뮬레이션 여부 |
| `succeeded`, `error` | 결과 |
| `occurred_at` | 언제 |
| `on_behalf_of`, `is_agent` | 에이전트 수행 맥락 |

`changes`에 GIN 인덱스가 있어 특정 객체의 변경 이력을 추적할 수 있고,
실패/거부만 보는 부분 인덱스도 있다.

> **현재 API 라우터는 `InMemoryAuditSink`를 쓴다.** 프로세스가 재시작되면
> 기록이 사라진다. `PostgresAuditSink`로 교체하는 것이 배포 전 필수 작업이다
> (`docs/07_개선_로드맵.md` 참조).

## AIP와의 대응

AIP Agent Studio의 도구는 세 종류다.

| AIP | 이 프로젝트 |
|---|---|
| **Object query tool** (필터·집계·링크 순회) | `analytics/src/agent/tools.py` — 구조는 맞으나 아직 하드코딩 샘플 |
| **Action tool** (온톨로지 편집 실행, 자동 또는 사용자 확인 후) | **이 계층.** `GET /api/actions/{type}`이 도구 정의를 그대로 제공 |
| **Function tool** | 분석 함수들 (SPC, 이상탐지) |

`requiresHumanConfirmation: true`인 액션은 AIP의 "사용자 확인 후 실행"에
대응한다. 에이전트는 `simulate`로 예상 결과를 보여주고, 사람이 승인하면
실제 수행한다.

## 남은 작업

핸들러는 변경 계획(`changes`) 계산과 감사 기록까지 완료돼 있고,
실제 저장소 반영은 대상 서비스 연동 후 채운다. 각 핸들러의 TODO 참조.

- [ ] `VerifyRelationship` → `RelationshipStore` 연결
- [ ] `AcknowledgeAlarm` → 알람 저장소 연결
- [ ] `UpdateEquipmentState` → 현재 상태 조회 후 전이 검증 활성화 + 상태 이력 적재
- [ ] `HoldLot` → MES 연동 (읽기 전용이면 지시 큐 적재)
- [ ] `RequestInspection` → 점검 지시 저장소 + 담당자 배정
- [ ] `InMemoryAuditSink` → `PostgresAuditSink`
- [ ] 기존 쓰기 엔드포인트(ontology, analytics 라우터)를 Action 경유로 이관

마지막 항목이 중요하다. Action 경로를 만들어도 **옆에 직접 쓰기 경로가
남아 있으면 통제가 새어 나간다.**
