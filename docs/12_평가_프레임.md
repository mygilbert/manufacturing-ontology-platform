# 평가 프레임 (Evals) — 역량질문이 답해지는지 숫자로 잰다

`docs/11_AIP_구성_분석.md` 의 AIP-like 6요소 중 **5번**에 해당한다.
원천은 `docs/05_역량질문.md` 다.

## 왜 지금 만들었는가

실데이터가 없는데 평가부터 만드는 것이 거꾸로 보일 수 있다. 그렇지 않다.

**지금 만들어야 "데이터 투입 전 → 투입 후" 비교가 가능하다.**
나중에 만들면 before 가 없어 진척을 증명할 수 없고, 사내 보고에 쓸 수 없다.

그리고 평가 대상의 상당수는 데이터와 무관하다 — 권한 통제, 사유 요구,
레거시 코드 거부 같은 것들은 지금 이미 검증된다.

## 핵심 설계

### 1. "답 못 함"과 "틀림"을 구분한다

| 상태 | 의미 | 분모 포함 |
|---|---|---|
| `PASSED` | 지금 답한다 | O |
| `FAILED` | 답하는데 기준 미달 | O |
| `NOT_IMPLEMENTED` | **아직 답할 수 없다** | **O** |
| `ERROR` | 실행 중 오류 (보통 테이블 없음) | O |
| `SKIPPED` | 건너뜀 | X |

`NOT_IMPLEMENTED` 를 분모에서 빼면 점수가 부풀려지고 진척이 안 보인다.
반대로 `FAILED` 와 뭉치면 "고쳐야 할 버그"와 "아직 안 만든 기능"이 섞인다.
둘은 대응이 다르므로 분리한다.

미구현 케이스는 **왜 못 하는지**를 반드시 적는다. 그 사유가 그대로 로드맵이 된다.

```yaml
- id: E4
  question: "통계로 발견됐지만 미검증인 관계를 구분할 수 있는가"
  target:
    type: not_implemented
    note: "RelationshipStore 가 아직 그래프에 연결되지 않았다 (docs/07 P0-3)"
```

### 2. 온톨로지 편집은 시뮬레이션에서 실행한다

Action 타겟은 러너가 **항상 `dry_run=True` 로 강제**한다.
스위트에서 끌 수 없다.

평가가 실제 상태를 바꾸면 그 평가는 한 번밖에 못 쓴다.
AIP Evals 가 온톨로지 편집 케이스를 시뮬레이션에서 실행하는 것과 같은 이유다.

`dry_run_wrote_nothing` 채점기가 결과에 시뮬레이션 표시가 남았는지 확인한다.

### 3. 채점기 없는 케이스는 통과하지 않는다

무엇을 검증하는지 적지 않은 케이스가 통과하면 점수가 거짓이 된다.
채점기가 비어 있으면 `no_grader` 불합격으로 처리한다.

### 4. 정의는 YAML, 실행은 코드

테스트 케이스는 도메인 담당자가 읽고 고칠 수 있어야 한다.
`evals/suites/competency_battery.yaml` 참조.

## 구조

```
evals/suites/*.yaml          스위트 정의 (추적됨 — 코어 자산)
evals/results/               리포트 산출 (.gitignore — 아래 주의 참조)

common/evals/
  types.py       Status / TestCase / CaseResult / SuiteResult
  graders.py     채점기
  runner.py      타겟 실행 (sql / action / not_implemented)
  report.py      콘솔 + Markdown + JSON

scripts/run_evals.py         CLI
```

> **주의** `evals/results/` 는 `.gitignore` 대상이다.
> 리포트의 `evidence` 에 결과 첫 행 값이 담기는데, 실데이터로 돌리면
> 사내 Lot ID 같은 식별자가 들어간다. 스위트 정의만 추적한다.

## 타겟 3종

| 종류 | 설명 |
|---|---|
| `sql` | DuckDB 로 랜딩 Parquet 에 질의. 표준 테이블 이름 뷰를 쓴다 |
| `action` | Action 을 dry_run 으로 수행. 권한·검증·감사 통제를 검증 |
| `not_implemented` | 아직 답할 수 없는 케이스. 사유 필수 |

`sql` 타겟이 쓰는 표준 테이블 이름은 `common/evals/runner.py` 의
`CANONICAL_TABLES` 에 있다. 사이트 데이터도 매핑을 거쳐 같은 이름으로 올라오므로
**스위트를 고치지 않고 실데이터로 돌릴 수 있다.**

## 채점기

| 채점기 | 용도 |
|---|---|
| `not_empty` / `no_rows` | 결과 유무. `no_rows` 는 데이터 품질 점검용 |
| `row_count` | 행 수 범위 |
| `columns_present` | 컬럼 존재 |
| `top_row_equals` | 1순위 행 판정 (역추적 검증) |
| `value_between` | 첫 행 수치 범위 |
| `all_rows_match` | 모든 행이 허용값 집합 안인지 |
| `column_values_include` | 기대값이 결과에 나타나는지 |
| `action_succeeded` / `action_rejected` | 액션 성공/거부 |
| `changes_include` | 변경 목록에 기대 필드·값이 있는지 |
| `dry_run_wrote_nothing` | 시뮬레이션으로 실행됐는지 |

`action_rejected` 는 **거부돼야 통과**다. 권한 통제와 검증이 실제로 막는지
확인하는 데 쓴다 (D2 레거시 코드 거부, D3 권한 없음, E2 사유 누락).

## 실행

```bash
pip install duckdb pyarrow pyyaml
python scripts/generate_battery_genealogy.py   # 합성 데이터 (없으면)
python scripts/run_evals.py

python scripts/run_evals.py --case B2 --case B3   # 일부만
python scripts/run_evals.py --landing /site/data  # 실데이터로
python scripts/run_evals.py --fail-under 60       # CI 임계값
```

## 음성 대조 — 채점기가 실제로 변별하는가

합성 데이터는 스키마에 맞게 생성되므로 쉽게 통과할 수 있다.
그래서 일부러 망가뜨려 점수가 떨어지는지 확인했다.

| 조작 | 결과 |
|---|---|
| 음극 계보 제거 (`supplies_cell` 에서 ANODE 삭제) | 22 → 21. **A1 실패** (`row_count: 1행, min=2`) |
| 이상 구간 제거 (모든 두께를 USL 아래로) | 22 → 18. **B1·B2·B3·B4 실패** |

두 번째가 특히 중요하다. 이상을 없애니 이상 탐지 관련 네 케이스가 정확히
떨어졌다. 채점기가 데이터를 실제로 보고 있다는 뜻이다.

## 실데이터가 오면

스위트를 고치지 않고 `--landing` 만 바꾼다.

```bash
python scripts/run_evals.py --landing /path/to/site/landing
```

예상되는 변화:

- **ERROR 증가** — 없는 테이블·컬럼이 드러난다. 이것이 매핑 작업 목록이 된다
- **F 계열(데이터 품질) 하락** — 조인 실패, 추적 신뢰도 저하가 실제로 나타난다
- **F4 활성화** — 다중 소스라 시간대 일관성 검증이 가능해진다
- **B 계열 변동** — 실제 이상이 있으면 탐지되고, 없으면 떨어진다

합성 75.9% → 실데이터 첫 실행에서 몇 %가 나오는지가
**현재 추적성 수준의 정직한 측정치**다.
