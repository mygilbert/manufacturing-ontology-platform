# 표준 적용 가이드

## 요지

제조 설비/공정 온톨로지는 **바닥부터 만들 필요가 없다.**
특히 반도체는 이미 표준화된 장비 객체 모델이 존재한다.
자체 용어로 모델링하면 사내 기존 집계(가동률, OEE)와 수치가 어긋나고,
나중에 외부 시스템과 연계할 때 전부 다시 매핑해야 한다.

이 문서는 이 프로젝트가 채택한 표준과, 각 표준이 어느 스키마 파일에
어떻게 반영됐는지를 정리한다.

| 표준 | 내용 | 적용 대상 | 반영 상태 |
|---|---|---|---|

| **SEMI E125 (EqSD)** | 장비 자기 기술 | 설비 메타데이터 수집 | 미적용 |
| **SEMI E164** | EDA 공통 메타데이터 | 파라미터 명명 체계 (`Sensor.param_id`) | 부분 |
| **SEMI E134** | 데이터 수집 관리 | 수집 계획 | 미적용 |
| **SEMI E10 / E58** | 설비 상태 모델 (RAM) | `Equipment.status`, `Chamber.status` | 반영 |
| **ISA-95 / IEC 62264** | Enterprise→Site→Area→WorkCenter→WorkUnit 계층, 작업 수행 이력 | 설비 계층, `PROCESSED_AT` | 부분 |
| **W3C SSN/SOSA** | Sensor / Observation / FeatureOfInterest / ObservedProperty 관측 패턴 | `Sensor`, `Measurement`, `OBSERVES` | 반영 |

## 2. SEMI E10 — 설비 상태 모델

### 왜 바꿨나

기존 `RUNNING / IDLE / PM / DOWN / ENGINEERING`은 자체 용어였다.
자체 용어를 쓰면 이 시스템이 계산한 가동률과 사내 기존 리포트의 가동률이
달라지고, 반드시 "어느 쪽이 맞느냐"는 논쟁이 생긴다.
SEMI E10은 반도체 업계 표준이므로 여기에 맞추면 그 논쟁이 사라진다.

### 6 기본 상태

| 상태 | 정의 |
|---|---|
| `PRODUCTIVE` | 의도된 기능 수행 중. 정규 생산, 제품 로드/언로드, 재작업, 생산 테스트, 생산과 병행한 엔지니어링 런 포함 |
| `STANDBY` | 비조업 시간이 아니면서, 수행 가능한 상태이나 가동하지 않음. 작업자 없음/제품 없음/지원 도구 없음/생산 테스트 결과 대기 |
| `ENGINEERING` | 수행 가능한 상태에서 엔지니어링 실험을 수행 중. 공정 엔지니어링, 설비 엔지니어링 |
| `SCHEDULED_DOWNTIME` | 계획된 비가동 이벤트로 수행 불가. 정기 정비 등 |
| `UNSCHEDULED_DOWNTIME` | 계획되지 않은 비가동 이벤트로 수행 불가. 비계획 정비 등 |
| `NON_SCHEDULED` | 비조업 시간. 미배정 교대, 설비 미설치, 셧다운 |

### 마이그레이션

`equipment.yaml`의 `status.legacyMapping`에 기존 코드 → E10 매핑을 선언해 뒀다.
레거시 데이터 적재 시 이 매핑을 적용한다.

```
RUNNING     -> PRODUCTIVE
IDLE        -> STANDBY
PM          -> SCHEDULED_DOWNTIME
DOWN        -> UNSCHEDULED_DOWNTIME
ENGINEERING -> ENGINEERING
(신규)       -> NON_SCHEDULED
```

사내 고유의 세부 사유 코드는 `e10_substate` 속성에 담는다.
**기본상태는 표준으로 고정하고, 사내 구분은 하위에 둔다.**

## 3. SEMI E120 — 설비 구조

### 왜 Chamber를 별도 객체로 분리했나

기존에는 `Equipment.chamber_count`라는 숫자 속성만 있었다.
이래서는 다음 질문에 답할 수 없다.

- "EQP-001 챔버2를 지나간 Lot은?"
- "챔버별 공정능력이 다른가?"
- "챔버 교체 전후로 거동이 달라졌나?"

FDC 데이터는 대부분 챔버 단위로 수집되고, 이상도 챔버 단위로 발생한다.
따라서 챔버는 온톨로지의 1급 객체여야 한다.

E120은 설비를 Module / Subsystem / IODevice로 분해하며, 챔버는
Process Module에 해당한다. `chamber.yaml`의 `module_type`이 이 분류를 따른다.

```
Equipment ──HAS_MODULE──> Chamber (module_type: PROCESS_MODULE)
                                 ├─ LOAD_PORT
                                 ├─ TRANSFER_MODULE
                                 └─ ...
```

## 4. W3C SOSA — 관측 패턴

### 왜 센서와 관측 대상을 분리했나

기존 `Measurement` 객체는 센서와 관측 대상이 섞여 있었다.
실제로는 네 가지가 모두 다른 개념이다.

```
Observation (관측 1건)
  ├─ sosa:madeBySensor        -> Sensor          (TEMP_001)
  ├─ sosa:observedProperty    -> ObservedProperty (온도)
  ├─ sosa:hasFeatureOfInterest -> Chamber         (EQP-001 챔버2)  ← 관측 대상
  ├─ sosa:resultTime          -> 2026-09-26T14:03:22
  └─ sosa:hasSimpleResult     -> 47.2
```

분리하지 않으면 **"센서를 교체한 뒤에도 같은 대상의 데이터를 이어서 볼 수
있는가"**에 답할 수 없다. 한 센서가 여러 대상을 관측하는 경우도 표현하지 못한다.

### 파라미터 정규화

`Sensor`에 `param_id`(소스 원본)와 `observed_property`(정규화된 이름)를
둘 다 둔다. 설비 벤더별로 같은 물리량을 다른 이름으로 올리기 때문에,
**설비 간 비교는 반드시 `observed_property`로 해야 한다.**

## 5. 저장 위치 원칙 — 그래프에 무엇을 넣지 않을 것인가

| 대상 | 그래프(AGE) | TimescaleDB |
|---|---|---|
| Equipment, Chamber, Lot, Wafer, Recipe, Process, Sensor | O | |
| 관계 엣지 (PROCESSED_AT, HAS_MODULE, OBSERVES 등) | O | |
| 발견된 관계 + 전문가 지식 | O | |
| **FDC/SPC 시계열 측정값** | **X** | O |

측정값을 그래프 노드로 만들면 노드 수가 수억 개로 폭발하고 AGE가 버티지 못한다.
`measurement.yaml`의 `storage.graphNode: false`가 이 원칙을 선언한다.

그래프에서는 `Sensor -OBSERVES-> Chamber` 경로로 접근하고,
실제 값은 TimescaleDB에서 `(sensor_id, timestamp)` 범위 질의로 가져온다.

## 6. 도메인 온톨로지 ≠ KG 스키마

Bosch 저항용접 사례의 핵심 교훈이다.

- **도메인 온톨로지**는 *지식 지향*이어야 한다 — 데이터의 particularity가 아니라
  일반적 도메인 지식을 반영
- **KG 스키마**는 *데이터 지향*이어야 한다 — 실제 데이터 특성을 전부 커버

도메인 온톨로지를 그대로 KG 스키마로 쓰면 다음이 발생한다.

- 데이터에 매핑되지 않은 클래스 때문에 **blank node** 대량 생성
- 그래프가 불필요하게 깊어져 2홉이면 될 질의가 5홉이 됨
- 사용자의 **질의 작성 학습 시간 증가**
- 중복 정보로 **저장공간 낭비**
- **유지보수·갱신 난이도 상승**

### 이 프로젝트에서의 의미

`ontology/schemas/**/*.yaml`은 **도메인 온톨로지**다.
AGE에 실제로 적재되는 그래프 구조는 이것과 **달라도 된다.**

- YAML에 선언된 속성을 전부 그래프 노드 속성으로 밀어넣지 않는다
- 질의에 실제로 쓰이는 속성만 그래프에 올린다
- 나머지는 관계형 테이블에 두고 키로 참조한다

또한 Atlas Copco 사례의 교훈:
**DB 스키마에서 온톨로지를 자동 생성하지 말 것.**
그러면 솔루션 영역의 기술적 데이터 구조에 편향되어 문제 영역을 반영하지 못한다.
도메인 모델은 (데이터를 본 다음에) 손으로 만든다.

## 7. 관계 메타데이터 규약

모든 관계 엣지는 아래 메타데이터를 가진다.
`relationship_store.py`의 `DiscoveredRelationship`이 이를 구현한다.

| 필드 | 의미 | 필수 |
|---|---|---|
| `origin` | 관계의 출처: `structural` / `expert` / `discovered` | O |
| `confidence` | 신뢰도 0~1 | O |
| `method` | 도출 방법 (`granger`, `pearson`, `mes_join`, `interview` 등) | O |
| `evidence_*` | 근거 (p_value, n, lag_sec 등). 그래프 질의에서 필터링 가능하도록 펼쳐 저장 | 발견된 관계는 필수 |
| `verification_status` | `pending` / `verified` / `rejected` | O |
| `verified_by`, `verified_at` | 검증자와 검증 시각 | 검증 시 필수 |
| `valid_from`, `valid_to` | 유효 기간. 설비 개조/레시피 변경 시 기존 엣지를 닫고 새로 만든다 | O |

### origin을 반드시 남기는 이유

6개월 뒤에 "이 관계는 사람이 넣은 것인가, 기계가 찾은 것인가"를
아무도 알 수 없게 되면 그래프 전체를 신뢰할 수 없게 된다.

### 3계층 출처

| 계층 | origin | 성격 | 신뢰도 |
|---|---|---|---|
| 1 | `structural` | 키 + 시간구간 조인으로 도출된 사실 | 100% |
| 2 | `expert` | 엔지니어가 입력한 도메인 지식 | 높음 (검증됨) |
| 3 | `discovered` | 통계 분석이 제시한 **가설** | 낮음 (검증 필요) |

### 승격 관문

통계 신뢰도만으로 관계를 승격시키지 않는다.
신뢰도가 높다는 것은 "데이터에서 강하게 보인다"이지 "물리적으로 맞다"가 아니다.

```
discovered
   ↓ ① 전문가 지식의 "불가능한 관계" 필터 (RelationshipValidator)
   ↓ ② 물리적 타당성 (lag 방향이 공정 순서와 모순되지 않는가)
   ↓ ③ 재현성 (다른 기간 / 다른 설비에서도 나타나는가)
pending → 엔지니어 검토 → verified / rejected
```

`_auto_verify()`는 이 원칙에 따라 신뢰도만으로는 승격시키지 않도록 수정됐다.

### 상관관계 해석 시 주의

같은 챔버의 두 파라미터는 거의 항상 강한 상관이 나온다.
인과여서가 아니라 **레시피 스텝이 동시에 바뀌기 때문**이다.
반드시 **레시피 스텝 구간 안에서만** 상관을 보고, 같은 레시피·같은 챔버
조건끼리만 비교한다.

또한 **lag(시차) 없는 인과관계는 쓸모가 없다.**
`A → B`만으로는 엔지니어에게 줄 것이 없고,
`A → B (lag 3초)`가 있어야 "A가 흔들린 뒤 3초 안에 B를 보라"는
점검 순서가 나온다.
