# 개선 로드맵

실데이터(사내 FDC/SPC/MES) 연동을 앞두고 정리한 현황과 남은 과제.

## 현재 상태 요약

| 영역 | 평가 | 비고 |
|---|---|---|
| 아키텍처 설계 | 상 | CDC→Kafka→Flink→AGE/Timescale→API→React 일관성 있음 |
| 도메인/온톨로지 모델링 | 상 | 표준(SEMI/ISA-95/SOSA) 반영 완료 |
| 분석 알고리즘 깊이 | 중상 | SPC, 이상탐지 앙상블, Granger/Transfer Entropy |
| 프론트엔드 | 중 | 화면은 갖춰짐. `strict: false`로 타입 느슨 |
| 실제 연결 완성도 | 중하 | Agent 도구가 하드코딩 샘플, 관계 저장 루프 미완 |
| 보안 | 중 | Cypher 이스케이프 처리 완료. **인증 여전히 없음** |
| 테스트/CI | 하 | pytest 도입 시작. CI 없음 |

## 배치 수집 구조에서의 기대치 합의

**1시간 배치면 탐지 지연이 최소 1시간, 실제로는 1~2시간이다.**
프로젝트 시작 전에 이걸 명확히 해두지 않으면
나중에 "왜 실시간이 아니냐"는 질문에 걸린다.

| 요구 | 가능 여부 |
|---|---|
| 이상 발생 시 즉시 설비 정지·Lot 홀드 | 불가 (스트리밍 필요) |
| 시간 단위 스캔으로 이상 구간 조기 포착 | 가능 |
| **불량 발생 시 근본원인 역추적** | 가능 — 핵심 가치 |
| 설비·공정 간 숨은 관계 발견 | 가능 |
| SPC 관리도·공정능력 추세 모니터링 | 가능 |
| 선행지표 기반 예측 | 가능 |

### 스트리밍 전환 판단 기준

Kafka/Flink는 **제거하지 않고** compose 프로파일로 분리해 뒀다
(`--profile streaming`). 데이터를 본 뒤 아래로 판단한다.

| 항목 | 배치로 충분 | 스트리밍 필요 |
|---|---|---|
| 탐지 후 조치까지 허용 시간 | 수 시간 | 수 분 이내 |
| 실제 요구 | 원인분석·추세·예방 | 설비 정지·Lot 홀드 |
| **소스 적재 지연** | 이미 수십 분씩 밀림 | 소스가 거의 실시간 |
| 데이터량 | 시간당 처리 여유 | 배치창을 못 맞춤 |
| 운영 인력 | 제한적 | Kafka 운영 가능 |

세 번째가 결정적이다. **소스 FDC/MES가 이미 30분씩 밀려서 적재되고 있다면
Kafka를 붙여도 실시간이 되지 않는다.** 앞단이 병목이면 뒷단만 빨라져도
의미가 없다.

하이브리드가 현실적인 답일 가능성이 높다.

- 알람·트립 이벤트 (양 적음, 긴급도 높음) → 실시간
- FDC 파라미터 대량 측정값 → 배치
- MES track 이력 → 배치

## 구축 순서

```
[지금 — 데이터 없이 가능]
 0. 역량질문 확정 (엔지니어와)            ← 출발점
 1. 전문가 지식 인터뷰 착수               ← 리드타임이 길다

[샘플 데이터 도착 후]
 2. DuckDB로 조인 검증 (P1-5)
 3. sourceMapping에 실제 컬럼 채우기
 4. 계층1 관계 생성 (키 + 시간구간 조인)   ← 여기서 첫 가치
 5. 계층2 지식 적재
 6. 계층3 발견 실행 (계층2를 필터로)
 7. 역량질문으로 평가
```

**계층1을 건너뛰고 계층3부터 하는 것이 가장 흔한 실패 패턴이다.**
제품 축과 설비 축이 이어지지 않은 상태에서 찾은 관계는 검증할 방법이 없다.
