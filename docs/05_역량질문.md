# 역량질문 (Competency Questions)

## 이 문서의 목적

역량질문은 **온톨로지가 답할 수 있어야 하는 질문 목록**이다.
모델링을 시작하기 전에 먼저 쓰고, 완성 후에는 그대로 평가 기준이 된다.

산업용 지식그래프 구축 절차 모델(CRISP-DM 기반)은 역량질문을 전체 개발
사이클에 걸쳐 사용할 것을 권고한다. Bosch SMT 사례에서도 "품질 분석 과제
카탈로그"를 SPARQL 질의로 인코딩해 온톨로지를 평가했다.

**역량질문이 없으면 온톨로지가 완성돼도 "그래서 이게 뭘 답해주는가"에
답할 수 없고, 평가할 방법도 없다.**

## 사용법

1. 엔지니어와 함께 아래 질문을 검토하고, 현장에서 실제로 묻는 형태로 고친다
2. 우선순위를 매긴다 (P0: 없으면 프로젝트 의미 없음 / P1: 중요 / P2: 있으면 좋음)
3. 각 질문이 요구하는 객체·관계·속성을 확인한다 (아래 표의 "필요 요소")
4. 구현 후 각 질문을 실제 질의로 작성해 답이 나오는지 확인한다

> 상태는 구현 진행에 따라 갱신한다: `미착수` / `부분` / `완료`

## A. 추적성 (Traceability)

제품 축과 설비 축을 잇는 질문. **여기가 안 되면 나머지는 의미가 없다.**

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| A1 | LOT-xxxx가 거쳐간 설비·챔버·레시피를 시간순으로 나열하라 | P0 | `Lot -PROCESSED_AT-> Equipment/Chamber` (start/end/recipe/pass_no) | 미착수 |
| A2 | 이 웨이퍼가 속한 Lot과, 그 Lot의 형제 웨이퍼는 | P0 | `Wafer -BELONGS_TO-> Lot` | 미착수 |
| A3 | 특정 시각에 EQP-xxx 챔버2에서 처리 중이던 Lot은 | P0 | 시간구간 역조회 | 미착수 |
| A4 | 이 Lot이 재작업된 이력이 있는가, 몇 회차인가 | P1 | `PROCESSED_AT.pass_no`, `result=REWORK` | 미착수 |
| A5 | 이 설비를 지나간 Lot 중 최근 24시간 내 것을 모두 찾아라 | P1 | 시간 인덱스 | 미착수 |

## B. 이상 감지 · 원인 추적 (Anomaly & Root Cause)

이 시스템의 핵심 가치. 배치 수집 구조에서도 성립하는 질문들이다.

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| B1 | 이 불량 Lot들이 공통으로 거쳐간 설비/챔버/레시피가 있는가 | P0 | 교집합 질의 | 미착수 |
| B2 | ALM_xxx 발생 30분 전, 같은 챔버의 파라미터 거동은 어땠나 | P0 | `Alarm` + 시계열 구간 조회 | 미착수 |
| B3 | 이 파라미터가 스펙을 이탈했을 때 영향받은 Lot을 전부 찾아라 | P0 | 스펙 + 시간구간 + `PROCESSED_AT` | 미착수 |
| B4 | 이 알람의 알려진 원인 후보와 점검 순서는 | P0 | 전문가 지식 (알람-원인, 선행지표) | 부분 |
| B5 | 이상이 발생한 파라미터의 상류 원인 파라미터는 (lag 포함) | P1 | 인과 관계 + `lag_seconds` | 부분 |
| B6 | 같은 이상이 과거에도 있었나, 그때 원인은 무엇으로 판정됐나 | P1 | 이상 이력 + 검증된 관계 | 미착수 |
| B7 | 이 설비의 PM 직후 처리된 Lot에서 이상률이 높아지는가 | P1 | `Chamber.last_pm_date`, `wafer_count_since_pm` | 미착수 |
| B8 | 현재 열려 있는(미해제) 알람과 그 영향 범위는 | P2 | 알람 상태 | 부분 |

## C. 품질 · SPC

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| C1 | 레시피 R-xx를 사용한 설비 중 Cpk가 1.33 미만인 것은 | P1 | SPC 지표 + `USES_RECIPE` | 부분 |
| C2 | 이 파라미터의 관리도에서 웨스턴일렉트릭 룰 위반 이력은 | P1 | 관리도 판정 결과 | 부분 |
| C3 | 챔버별로 동일 레시피의 공정능력이 유의하게 다른가 | P1 | `Chamber` 단위 집계 | 미착수 |
| C4 | 스펙(USL/LSL)이 언제 어떻게 바뀌었고, 그 전후 판정이 달라지는가 | P2 | 스펙 버전/유효기간 | 미착수 |

## D. 설비 상태 · 가동률

SEMI E10 상태 모델을 따르면 사내 기존 집계와 수치가 맞물린다.

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| D1 | 이 설비의 E10 상태별 시간 분포는 (Productive/Standby/...) | P1 | `Equipment.status` (SEMI E10) | 미착수 |
| D2 | Unscheduled Downtime의 원인 알람 분포는 | P1 | 상태 이력 + 알람 연결 | 미착수 |
| D3 | 챔버 교체 전후로 파라미터 거동이 달라졌는가 | P2 | `HAS_MODULE.installed_at/removed_at` | 미착수 |

## E. 관계 · 지식 거버넌스

발견된 관계를 신뢰할 수 있게 만드는 질문. **이게 없으면 그래프를 믿을 수 없다.**

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| E1 | 이 관계는 누가 언제 어떤 근거로 넣었나 | P0 | `origin`, `evidence`, `verified_by`, `verified_at` | 부분 |
| E2 | 통계로 발견됐지만 아직 검증 안 된 관계 목록은 | P0 | `verification_status=pending` | 완료 |
| E3 | 전문가가 "불가능"이라고 표시한 관계를 통계가 다시 제안했는가 | P1 | 금지 관계 필터 + 검증기 | 부분 |
| E4 | 설비 개조 이후에도 여전히 유효한 관계인가 | P1 | `valid_from` / `valid_to` | 부분 |
| E5 | 이 관계가 다른 기간/다른 설비에서도 재현되는가 | P1 | 재현성 검증 | 미착수 |

## F. 데이터 품질 (운영)

배치 수집 구조에서 조용히 틀어지는 것을 잡는 질문.

| # | 질문 | 우선순위 | 필요 요소 | 상태 |
|---|---|---|---|---|
| F1 | 어느 파일까지 처리됐고, 실패한 배치는 무엇인가 | P0 | `ingest_log` | 미착수 |
| F2 | Lot에 연결되지 못한 측정값 비율은 (조인 실패율) | P0 | 조인 결과 통계 | 미착수 |
| F3 | FDC와 MES의 시각 오프셋은 얼마인가 | P0 | 발생시각 vs 수집시각 | 미착수 |
| F4 | 챔버를 특정하지 못한 처리 이력 비율은 | P1 | `PROCESSED_AT.chamber_resolved` | 미착수 |
| F5 | 아직 닫히지 않은(track_out 미도착) 처리 구간은 | P1 | `PROCESSED_AT.interval_closed` | 미착수 |

## 엔지니어 인터뷰용 질문 (계층2 지식 수집)

엔지니어에게 "온톨로지를 그려달라"고 하면 아무것도 나오지 않는다.
**업무 그대로의 질문**으로 물어야 한다. 아래 6개가
`create_expert_knowledge_template.py`가 만드는 엑셀 6개 시트와 대응한다.

| 질문 | 대응 시트 | 얻는 것 |
|---|---|---|
| "이 알람 뜨면 **뭐부터** 보세요? 그다음은요?" | 2.알람원인 / 3.선행지표 | 알람-원인 + 점검 순서 |
| "이 불량 나오면 어느 공정을 의심하세요? 왜요?" | 1.인과관계 | 근본원인 후보 |
| "터지기 전에 미리 보이는 신호가 있나요? 얼마나 전에요?" | 3.선행지표 | 선행지표 + **lag** |
| "이 파라미터 올리면 뭐가 같이 움직여요?" | 1.인과관계 / 4.파라미터그룹 | 파라미터 간 영향 |
| "**이건 절대 원인일 리 없다**는 게 있나요?" | 5.불가능한관계 | 오탐 필터 ★ |
| "이 파라미터는 정확히 뭘 재는 건가요? 정상 범위는?" | 6.파라미터정의 | 파라미터 정의 |

마지막에서 두 번째 질문이 결정적이다. 통계 분석이 내놓는 거짓 양성을
걸러내는 유일한 장치가 "불가능한 관계" 목록이다.
**그래서 계층2(전문가 지식)가 계층3(통계 발견)보다 먼저다.**

### 현실적 목표

완벽한 도메인 지식 체계를 만들려 하면 1년이 걸리고 끝나지 않는다.
**자주 나는 알람 상위 10개에 대한 원인·점검순서 20~30개**면 충분히 시작된다.
